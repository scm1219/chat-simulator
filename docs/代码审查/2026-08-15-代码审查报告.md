## 1. 总体评价

项目整体**架构分层清晰、工程质量中上**：主进程按 database / llm / ipc / narrative / utils 分层，渲染进程按 stores / components / composables 组织；SQL 全层参数绑定、动态 UPDATE 有表名白名单与列名正则校验，注入防护到位；流式链路（StreamBatcher 批量聚合、Map 索引、streamingTick、虚拟列表）性能设计扎实；LLM JSON 输出的多级容错解析是同类项目中的亮点。

主要风险集中在四个方面：

1. **数据安全防线不完整**：API Key 全程明文落盘；生产环境 CSP 实际不生效；无 window.open / 导航拦截；全项目唯一的 `v-html` 渲染不可信聊天内容构成 XSS 入口。四者叠加（XSS → electronAPI → 明文 Key / 任意 IPC）形成完整攻击链。
2. **日常操作可触发的数据破坏**：最严重的一项是切换"思考模式"开关会静默清空所有关联群组的 API Key 与 baseURL；此外秒级时间戳级联删除会误删同秒消息、群组复制丢字段、记忆按姓名关联导致改名后失联。
3. **承诺但不生效的功能**：SOCKS5 代理无法工作、思考模式（MiniMax）必然 400、"流式输出"开关是死逻辑、防重复提交锁全部失效——都属于用户配置后必现失败或静默失效的功能性缺陷。
4. **并发与竞态**：llm:generate 无防重入/取消，前端切群组时存在 4 条独立的竞态路径（加载竞态、流式事件串群、监听器泄漏、虚拟列表 key 退化），在真实使用中容易遇到"消息串群、顺序错乱"。

## 3. 严重问题（2 项）

### S-1 切换"思考模式"开关会静默清空所有关联群组的 API Key 和 baseURL

- **位置**：`electron/ipc/handlers/config.js:200-215`（触发链入口 `config.js:97-105`）
- **证据**：`updateLLMProfile`（llm-profiles.js:151-155）是**合并更新**语义（`{...profiles[index], ...data}`），而前端 `LLMConfigPanel.vue:253-255` 切换思考模式时只传 `{ thinking_enabled }` 部分字段。`syncGroupsProfile` 随即用**合并前的原始 data** 同步群组：

  ```js
  newProfileData.provider || oldProfile.provider,   // 有旧值兜底 ✓
  newProfileData.model || oldProfile.model,          // 有旧值兜底 ✓
  newProfileData.apiKey ? String(newProfileData.apiKey) : null,   // 无兜底 → null ✗
  newProfileData.baseURL ? String(newProfileData.baseURL) : null, // 无兜底 → null ✗
  ```

- **影响**：用户在配置面板点一次思考模式开关，所有使用该 profile 的群组 `llm_api_key`、`llm_base_url` 被静默清空并强制 `use_global_api_key = 1`，无任何提示。日常操作触发的静默数据破坏。
- **建议**：`syncGroupsProfile` 改用 `updateLLMProfile` 返回的**合并后完整 profile**（config.js:98 的 `result.data`）来同步，四个字段统一兜底。

### S-2 全局搜索结果 `v-html` 渲染不可信内容，构成 XSS

- **位置**：`src/components/layout/GroupSearch.vue:34、43`（渲染）、`96-103`（`highlightKeyword`）
- **证据**：这是全项目仅有的 `v-html` 使用点，`text` 为消息 snippet（主进程 search.js:27-64 直接取自数据库，即用户输入 + LLM 输出）：

  ```js
  const escaped = kw.replace(/[.*+?^${}()|[\]\\]/g, '\\&')  // 只转义了正则元字符
  return text.replace(regex, '<mark class="search-highlight">$1</mark>')  // 未做任何 HTML 转义
  ```

- **影响**：消息含 `<img src=x onerror=...">` 等内容时原样注入 DOM。角色扮演场景 LLM 输出 HTML 片段并不罕见；这是 Electron 渲染进程，脚本执行后可直接调用 `window.electronAPI` 全部 100+ IPC（读取全部群组数据、`group:delete`、读取明文 API Key 等）。生产 CSP 本应兜底，但见 H-3——生产 CSP 实际不生效，攻击链完整。
- **建议**：先对 `text` 做 HTML 实体转义（`& < > " '`）再做关键词替换；或改用 split + `<mark>` 插值的组件化方案，彻底去掉 `v-html`。

## 4. 高优先级问题（16 项）

### 安全防线

#### H-1 groupId 无校验：路径穿越可删任意文件 + 任意 ID 静默创建数据库
- **位置**：`electron/database/manager.js:296、403-406`；`electron/ipc/handlers/group.js:145-153` 等
- `path.join(this.dataDir, `group_${groupId}.sqlite`)` 中 groupId 全程来自渲染进程且无白名单校验。`groupId = "..\\..\\foo"` 时 `deleteGroupDB` 的 `unlinkSync` 可删除 userData 之外任意 `.sqlite` 结尾文件；`getGroupDB` 可在任意路径建库。另外 `undefined` 等任意 ID 也会静默创建 `group_undefined.sqlite` 垃圾库文件（查询类 handler 全部无存在性校验）。
- **建议**：入口校验 groupId 格式（UUID 正则），并校验解析后路径仍位于 dataDir 内；查询类入口用 `fileMustExist: true` 只读打开。

#### H-2 LLM API Key 多处明文落盘，未使用 safeStorage
- **位置**：`electron/database/manager.js:25`（groups 表）、`electron/config/manager.js:26/129`（llm-config.json）、`electron/config/llm-profiles.js:92`（llm-profiles.json）
- 全项目无 `safeStorage` 引用。任何能读取用户目录的进程、云同步盘、备份均可直接获得全部 API Key（有直接金钱价值）。
- **建议**：用 `safeStorage.encryptString()` 加密后存储，读取时解密；迁移时兼容旧明文格式。

#### H-3 生产 CSP 实际不生效 + 缺失窗口打开/导航拦截
- **位置**：`electron/main.js:38-49`（CSP）、`main.js:16-28`（BrowserWindow）
- 两项叠加：
  1. 生产用 `loadFile`（file://）加载，而 `onHeadersReceived` **只对 http/https 请求触发**，file:// 响应无响应头，回调根本不执行——生产环境实际运行在**无任何 CSP** 状态（index.html 也无 CSP meta）。开发环境同样无 CSP。
  2. 全 electron 目录无 `setWindowOpenHandler`、无 `will-navigate` 拦截。渲染进程一旦被注入，`window.open('https://evil.com')` 打开的子窗口**继承 preload**，恶意站点直接获得 electronAPI 全部能力——Electron 官方文档明确列出的经典攻击链。
- **建议**：在 index.html 加 CSP meta 标签（官方推荐方式），删除无效的 onHeadersReceived 代码，收紧 `connect-src`；补 `setWindowOpenHandler(() => ({ action: 'deny' }))` 与 `will-navigate` 白名单拦截；显式声明 `sandbox: true`。

### 必现功能失败

#### H-4 思考模式 budget_tokens 硬编码 10000，与 max_tokens=2000 必然冲突
- **位置**：`electron/llm/anthropic-client.js:184`（对照 167 行 `max_tokens: options.maxTokens || 2000`）
- Anthropic 协议要求 `max_tokens > thinking.budget_tokens`。主要调用方不传 maxTokens（恒 2000 < 10000），MiniMax 等兼容端点一旦开启思考模式**每次请求必然 400**，功能完全不可用。
- **建议**：`budget_tokens` 随 maxTokens 动态计算（如 `Math.max(1024, Math.floor(maxTokens * 0.8))`）且小于 max_tokens。

#### H-5 SOCKS5 代理在 UI 中承诺支持，但 axios 1.18.1 根本无法实现
- **位置**：`electron/llm/proxy.js:70、211`；宣传文案 `src/components/config/LLMProfileForm.vue:249`
- 已核对 axios 1.18.1 源码：仅内置 http/https 代理支持，无 socks-proxy-agent。`protocol: 'socks5'` 会导致 HTTP CONNECT 打到 SOCKS 端口或报 Unsupported protocol，**必现连接失败**，且报错文案（"网络连接失败"）完全指不到真实原因。
- **建议**：引入 `socks-proxy-agent`，检测 socks 协议时设置 `httpAgent/httpsAgent` 并 `proxy: false`；修复前先从 UI 移除 SOCKS5 宣传。

### 数据误删/丢失

#### H-6 按秒级 timestamp 级联删除消息，误删同一秒内的消息
- **位置**：`electron/ipc/handlers/message.js:100`、`electron/ipc/handlers/narrative.js:106-110`（根因 schema：manager.js:67 `timestamp DATETIME DEFAULT CURRENT_TIMESTAMP`，UTC 秒级精度）
- 用户消息与紧随的 AI 回复（并行模式下多个角色回复）落在同一秒是常态，"从此消息开始删除"（`timestamp >= ?`）会把同秒内位于目标消息**之前**的消息一并误删。narrative 版本还用 `content = ?` 匹配用户消息取最新一条，用户重发相同内容时会从更晚的消息开始删，误删中间全部正常聊天。
- **建议**：消息 timestamp 改为毫秒级（插入时显式写入 ISO 毫秒值）或增加单调序号；删除改为按 `rowid`/主键定位后 `rowid >= ?`；事件表记录触发消息的 message_id。

#### H-7 llm:generate 无防重入与取消机制，并发调用导致消息交错
- **位置**：`electron/ipc/handlers/llm.js:151-266`
- 入口无按 groupId 的进行中检查、无 AbortController。上一轮未完成时再次发送，两轮生成各自取历史快照、交错写库，按 timestamp 排序后消息顺序错乱；顺序模式下第二轮上下文缺失。全层无取消途径，切群组/删角色后进行中的调用继续执行。
- **建议**：维护 `Map<groupId, AbortController>`，新请求 abort 旧请求（客户端已支持 signal 传递框架）；或对同群组进行中请求直接返回"生成中"。

#### H-8 导出 ZIP 跨盘符 rename 必然失败（EXDEV）
- **位置**：`electron/ipc/handlers/message.js:192-211`
- 临时 ZIP 写在系统盘 Temp，`fs.promises.rename` 到用户选择的保存位置，Windows 下跨卷移动抛 `EXDEV`。本项目即 Windows 平台，用户导出到非系统盘必现失败。
- **建议**：改用 `copyFile` + 成功后删除临时文件，或直接在目标路径创建写流。

### 模块系统与日志可靠性

#### H-9 json-extractor.js 使用 CJS 导出，与 ESM 项目体系冲突
- **位置**：`electron/utils/json-extractor.js:129`（`module.exports = { extractJSON }`）
- package.json 为 `"type": "module"`，同层全部文件为 ESM。已实测 Node ESM 直接导入报 `SyntaxError`。当前仅靠 Vite 构建容错转换在运行，任何直接以 Node ESM 消费该文件的场景（单测、工具链升级）立即崩溃。
- **建议**：改为 `export { extractJSON }`。

#### H-10 Windows 日志轮转 rename 因句柄未释放失败，文件日志从此静默失效
- **位置**：`electron/utils/logger.js:111-117`
- `_sharedStream.end()` 是异步关闭，随后立即 `fs.renameSync`——Windows 不允许 rename 被持有的文件，抛 EPERM 被外层 catch 静默吞掉。此后流已关闭，**所有文件日志静默丢弃**直到日期切换。日志超 5MB 触发轮转即命中，console 输出正常造成"日志在工作"的假象。
- **建议**：在 `stream.end()` 回调中完成 rename；或超限时直接 truncate 重建流。

### 前端竞态（切群组场景）

#### H-11 虚拟列表未设置 getItemKey，key 退化为 index，编辑状态串扰可导致跨群消息内容被覆盖写库
- **位置**：`src/components/chat/ChatWindow.vue:236-241`（使用点 88-106）
- 已核对 @tanstack/virtual-core 3.17.4 源码：默认 key 即 index。切群组时同位置组件被 Vue 复用，本地状态（`editing`/`editContent`）残留。最严重链条：群 A 中对第 5 条消息进入编辑后切到群 B → 编辑框仍在且内容是群 A 文本 → blur 触发 `saveEdit` → **群 A 的内容被持久化写入群 B 的消息**。另导致测量缓存按 index 误用产生滚动跳动。
- **建议**：`useVirtualizer` 增加 `getItemKey: (i) => messagesStore.messages[i]?.id ?? i`。

#### H-12 流式/新消息事件均不校验 groupId，切群组后旧群消息污染当前视图
- **位置**：`src/stores/messages.js:143-206`（三个监听器）、`src/components/chat/ChatWindow.vue:568-602`（aftermath/message:new）
- 事件 payload 带有 `groupId` 但从不比对。LLM 生成持续数秒到数十秒，期间切群组：旧群的流式气泡、最终消息、余波消息全部 push 进新群消息列表，跨群数据串显直到下次重载。
- **建议**：所有 append 点统一守卫 `if (data.groupId !== groupsStore.currentGroupId) return`（建议收敛到 store 层）。

#### H-13 loadMessages / loadCharacters 无竞态保护，慢响应覆盖新群组数据
- **位置**：`src/stores/messages.js:24-42`、`src/stores/characters.js:17-21`（触发点 ChatWindow.vue:491-509）
- 快速从群 A 切到 B 时，若 A 的 IPC 响应后到（消息多的群更慢），B 界面最终显示 A 的消息/角色列表。情绪列表同理。
- **建议**：store 内引入请求序号（`const seq = ++loadSeq; if (seq !== loadSeq) return`）或返回后比对当前 currentGroupId 再落地。

#### H-14 setupMessageListener 防重复注册逻辑完全无效
- **位置**：`src/stores/messages.js:115-118`
- `window.electronAPI.message.onNewMessage(() => {})()` 是注册一个 no-op 又立即清理**它自己**，旧的 `messageListener` 从未被移除（已核对 preload.js:9-15 的清理语义）。且该监听器无清理出口。当前因 ChatWindow 静态挂载只触发一次而未爆发，任何条件渲染/路由化改造后立即产生监听器泄漏 + 每条消息重复 append。
- **建议**：改为 `messageListener?.()`；store 暴露统一 cleanup 并在组件 onUnmounted 调用。

### 配置数据污染

#### H-15 为供应商添加模型时，预填错误供应商的 API Key 和 baseURL
- **位置**：`src/components/config/LLMConfigPanel.vue:194-199`
- 取的是**全局第一个 profile**（任意供应商）而非按 providerId 过滤。点 Ollama 分组的 "+" 会把 OpenAI 的 Key 和 baseURL 预填进 Ollama 表单，用户直接保存即产生不可用配置，且 A 供应商 Key 被扩散到 B 供应商配置。
- **建议**：`profiles.value.find(p => p.provider === providerId)`，找不到时回退供应商默认值且 Key 留空。

#### H-16 "思考模式"字段双命名不一致，两个管理入口互相污染状态
- **位置**：`src/components/config/LLMConfigPanel.vue:55,226,254,269`（下划线 `thinking_enabled`）与 `src/components/config/LLMProfileDialog.vue:110,155-161`（驼峰 `thinkingEnabled`）
- 存储层按前端提交的原始字段名 merge。交叉使用后同一 profile JSON 中同时存在 `thinking_enabled: 1` 与 `thinkingEnabled: false` 两个矛盾的值，任一入口的修改在另一入口显示为相反状态。
- **建议**：统一为驼峰（与 streamEnabled/useNativeApi 一致），读取处做兼容迁移。

## 8. 做得好的方面

1. **SQL 注入防护体系扎实**：全层参数绑定；最易出注入的动态 UPDATE（handler-wrapper.js:37-64）有表名白名单 + 列名正则校验。
2. **迁移系统规范**：schema_migrations 版本表、每迁移事务包裹、pragma 检查幂等、失败中止不产生半迁移状态。
3. **流式渲染性能设计出色**：StreamBatcher 50ms 批量聚合（成功/失败/异常三条路径都保证 flush、定时器 unref）；messages store 用 Map 做 O(1) 索引 + streamingTick 优雅解决 Map 响应式盲区；虚拟列表正确处理了 vue-virtual 的 options 浅比较坑（getter 传 count）与动态高度测量；表格视图 v-memo、重型对话框按需异步加载。
4. **json-extractor 五级容错链**：代码块 → 直解析 → 去标记 → 括号截取 → 截断修复（含 inString 状态机处理字符串内截断与悬空转义），对 LLM 脏输出覆盖全面。
5. **statement-cache 的 WeakMap 设计**：以 Database 实例为键缓存 Statement，连接被 LRU 淘汰后缓存随 GC 自动回收，零手动清理。
6. **API Key 不进日志/前端纪律**：错误信息只用 statusMap 文案，日志只打 message 与状态码；前端 Key 输入 password 型带显隐、不回显、不落 localStorage。
7. **useApi 三档语义**（load/call/silent）+ `{success, data, error}` 统一协议，9 个 store 错误处理大体一致；store 间依赖严格单向无循环。
8. **Electron 基础隔离正确**：`nodeIntegration: false` + `contextIsolation: true`，preload 经 contextBridge 只暴露函数命名空间且监听器可清理；启动先注册全部 IPC 再建窗、退出前统一关闭数据库连接。
9. **预过滤共享优化**：角色无关的历史过滤一次执行、N 个角色共享，避免每角色重复遍历全量历史。
